# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

MC Wiki Race, a wiki race (like thewikigame.com) through minecraft.wiki: the player gets a random start and target article and must reach the target by clicking links inside articles, scored on clicks and time. The whole game is one `index.html` with no build step and no dependencies, plus `wiki-data.js`, which it loads with a script tag, and the link graph files `wiki-links.js` and `wiki-navboxes.js`, which it loads when a result works out par, all generated from an offline copy of the wiki (see Wiki data). Beside them are only static assets: the icon (`favicon.ico` at 16/32/48 px, `apple-touch-icon.png` at 180 px) and the 1200×630 link-preview image `og-image.png`. The name follows Mojang's usage guidelines, which forbid "Minecraft" as the first word or dominant part of a fan project's name. Its home is https://mcwikirace.com/ (BryantF.xyz/games/mc-wiki-race forwards there), and `<head>` has a meta description, Open Graph tags and a `canonical` link pointing there, so every copy of the page names that address as the original. The footer says who runs the game (BryantF.xyz, linked) and how to reach them, which the guidelines also ask for. Articles, pictures and descriptions are fetched live from the minecraft.wiki MediaWiki API at runtime, while what rolls pick from (the pool, link counts, hub redirects, namespaces) comes from `wiki-data.js`.

## Running

Open `index.html` directly in a browser (`file://` works; no server needed). `python3 -m http.server` also works if a real origin is wanted.

The setup screen puts playing first. Top to bottom: the daily (`.daily-box`: today's game in words, from `dailyText`, and how you did if you won it, from `renderDailyBox`, called by `renderHistory`; Play the daily is `#btnDaily`), Your game (`#gameSum`, filled by `updateSettingsSum`: the game with its option, the extra rules, the articles and the difficulty, and "Change game and settings ↓", which scrolls to them), the cards, Start game and par, and then, below a divider (`#gameSettings`), the steps: 1 · Choose a game (the tiles, `GAMES`, a radio group named `game`, read by `gameMode()`, with the strip under them, `#gameHelp` plus the picked game's own options, `.game-opt`: the checkpoint count, What to find and Exact clicks's count, `#exactInfo`, filled by `updateSetupPar`, and, while the cards are mostly off screen, "↑ See your cards", `#btnToCards`, which scrolls up to them; picking a game doesn't scroll by itself, since its options usually come next), 2 · Extra rules (`EXTRA_RULES`, boxes with a description each, in `#rules`, Round trip first), 3 · Articles and difficulty (one line, `updateSettingsSum`, and Change, which unfolds `#settings`: the pool, the difficulty, the target's topic and par, Content and Spin-offs). On a phone the cards lose their minimum height and show two lines of description, so Start game fits on the first screen. It ends with a footer (who runs it and a contact address, GitHub link, MIT license, credit for the wiki's CC BY-NC-SA 3.0 content, a non-affiliation notice). That licence asks reusers to link the pages they show, so during play the bottom of the path sidebar (`#credit`, set in `navigate`) links the current article on minecraft.wiki (`wikiUrl`) and the licence (collapsing the sidebar leaves it in a small box over the article's corner, with the button that brings the sidebar back), and the result dialog links every page in the path. Without JavaScript, a `<noscript>` style in `<head>` hides the setup controls and a `<noscript>` notice under the intro explains why.

A `#start=<Title>&target=<Title>` URL hash loads a fixed pair (this is what "Copy challenge link" produces), which is handy for testing a specific route. `#daily` loads today's daily pair and rule, and `#daily=YYYY-MM-DD` any past day's. A date that doesn't exist or hasn't come yet (by the player's local date, `dailyDate`) loads today's instead, so nobody can practise a daily before its day. An optional `&rules=noback` (comma-separated rule keys) sets the rules, the difficulty included (`setRules`: `nonav` is Normal, `nonav,nohubs` or `nohubs` alone Hard). A challenge link always sets them, so one without `rules` is Relaxed, as every game was before difficulty. They are applied even if the pair fails to load, and a daily replaces them with the day's. Each `&via=<Title>` adds a checkpoint, in order, up to three, and turns the Checkpoint rule on with that count. With Round trip too, `&back=N` says how many of them come after the target, on the way back (missing or out of range, it is moved to the nearest that fits). With Scavenger in `rules`, the target and the `via=` titles are its three articles instead, and each `&kind=<Category>` (in place of `target`) is one of its kinds.

## Wiki data

`wiki-data.js` is generated from the English Kiwix ZIM of minecraft.wiki, which is linked from [Minecraft Wiki:Offline use](https://minecraft.wiki/w/Minecraft_Wiki:Offline_use) and rebuilt quarterly. Don't edit it by hand. The ZIM (1.9 GB) is downloaded by hand from `https://download.kiwix.org/zim/other/` into the repo root. `.gitignore` keeps it out of git and only its checksum is committed (`sha256sum -c minecraft.wiki_en_all_2026-08.zim.sha256`). The tools in `tools/wikidata/` are Python, run in an ignored venv (`python3 -m venv .venv && .venv/bin/pip install -r tools/wikidata/requirements.txt`), always with `.venv/bin/python -I`:
- `extract.py <zim>` scans the ZIM (about a minute) into an ignored snapshot, `tools/wikidata/cache/<name>.jsonl.gz`. It holds every page's namespace (from mwoffliner's `ns-N` body class, since main-namespace titles can contain colons), visible categories and links. Links are split into those outside `.navbox` tables and each navbox's own (an outermost navbox table, nested tables included, as `boxes`; the page's own title is added to each, since a navbox shows the page it is on as plain text, so every copy of a navbox has the same titles; `Snapshot` derives `nav`, their union, from them), taken from the parser output only, and resolved against the page's own path as a browser would, since a subpage links to `../Diamond`. Redirects include mwoffliner's forwarding pages for redirects to a section.
- `build.py <snapshot> [-o folder]` writes `wiki-data.js`, `wiki-links.js` and `wiki-navboxes.js` (to the repo root by default) from the snapshot and `config.json`, which holds the hand-picked inputs: the topics (each a list of categories; an article goes to the first it is in), the categories and titles that aren't game content (other editions, list and set index pages), the Popular and Deep cuts shares, the Content families by category (`joke`, `removed`, `education`, `fiction`, `variants`, `mechanics`; the pool leaves their articles out), the spin-off namespaces, the disambiguation categories, the hubs and the core namespaces the ZIM doesn't hold, and Scavenger's kinds (`kinds`: hand-picked categories, approved 2026-10-21, each with the name the game shows and the members it leaves out). A kind's members are the pool articles in its category linked well enough to be a target, less its exclusions; the build stops if an excluded title has left its category or a kind has fewer than `MIN_KIND` (5) members, so a new snapshot gets the list looked at again. Every article and every spin-off page is listed. A pool-mode roll may only pick content: not a subpage, a disambiguation page, a version page (in a category ending in "versions") or a page that isn't game content. Such content gets its topic, or its family or spin-off instead, and the pool's articles get their tiers: Popular is the best-linked share of the pool, Deep cuts the least-linked share of each topic among articles linked well enough to be a target (`tiers` in `build.py`, which `report.py` also uses). Education is its four exact categories (blocks, items, entities, mobs), since the broad Minecraft Education category also holds Brewing, Charcoal and Dye. Links are counted per linking page, through redirects: an article's count only has links from articles, and a spin-off page's also has links from its own namespace, which are live when that spin-off is on. The same snapshot always gives the same bytes, one entry per line, so a new snapshot reads as a git diff.
- `report.py <snapshot>` writes a Markdown report (about 3 minutes): pool sizes, what moved to a Content family, each family's and spin-off's size and possible targets, link-count quartiles, Scavenger's kinds with every member (to read through before shipping a new snapshot), dead ends (articles with no route to the most linked one, so a game starting there can't be won), the pool designs compared, and hub candidates. The pool designs come from `config.json`'s `research` section (topics, categories that aren't game content, variant groups, Famous and Deep cuts shares), which only the report reads. Each design is measured on random pairs (`--pairs`, 200 by default, seeded by its name) with all links, without navboxes, and without navboxes or hubs: fewest clicks, good first clicks (links on the start page that begin a shortest route), the sweet spot and how familiar the ends are. `RESEARCH.md` records what the first run found.
- `diff.py <old> <new>` compares two `wiki-data.js` files, such as `<(git show HEAD:wiki-data.js) wiki-data.js`: pages added and removed, pool, family, spin-off and kind members that joined or left, link counts that moved, and hub and namespace changes.
- `test.py` writes a small ZIM in mwoffliner's shape and checks the other tools against it, in a few seconds.

The link graph numbers pages by their place in `wiki-data.js`'s `articles` and goes through redirects. `wiki-links.js` (`WIKI_LINKS`) lists each page's links outside navboxes: about 590,000 links, 1.6 MB, 0.6 MB gzipped. `wiki-navboxes.js` (`WIKI_NAVBOXES`) lists each distinct navbox once (about 1,150) and each page's navboxes: a tenth of the 4.9 million links every page's own list would hold, 1 MB, 41 KB gzipped. Normal and Hard only need the first, so Relaxed's navboxes are a file of their own. Each entry is page numbers as the gaps between them in base 36, one entry per line, and both files carry the ZIM's sha256, which the game checks against `wiki-data.js`'s.

To update: download the new ZIM, replace the `.sha256` file, run extract, build, diff and the test, play a few games, and commit the three generated files with the checksum.

## Architecture (all in `index.html`)

**API access.** Every request goes through `api()`, which always adds `origin=*`, allows at most `API_CONCURRENCY` (4) requests in flight with the rest queued in order (MediaWiki asks clients not to send many requests at once), and times each one out after 30 s. That parameter is mandatory: it is what makes MediaWiki send `Access-Control-Allow-Origin: *` for anonymous requests, and without it the page cannot fetch anything from `file://`. Calls used: `prop=pageprops|pageimages|extracts` (`pageInfo`: disambiguation flag, thumbnail, redirect resolution, and the description: the first paragraph of the TextExtracts plain-text intro, since `pageprops.description` is often an infobox caption and keeps HTML entities) and `action=parse` (article HTML, plus its live categories for Scavenger). Nothing polls; every request comes from a player action, and a roll makes one request.

**Picking articles.** Rolls draw titles from `wiki-data.js` (see Wiki data), which defines `WIKI_DATA`. `ARTICLES` maps every article and every spin-off page (titled `Dungeons:…`) to `{ links, body, topic, fams, tiers }`: how many pages link to it, how many of those from outside navboxes, its topic if it is in the pool, its Content (a family key such as `joke`, or its spin-off's name) and its tiers (`popular`, `deep`). Subpages, disambiguation, version and other non-content pages have neither topic nor Content, so only Chaos rolls them. `POOL` maps each topic (`TOPICS` holds their labels) to its articles and `POOL_TITLES` is their union. `CONTENT` maps each family key (`FAMILIES` holds their labels) and then each spin-off (`SPINOFFS`, name to namespace number) to the pages it adds, and `content()` lists the ones that are on, in that order. A rolled title is then looked up live with `pageInfo` for its description and picture, which also follows a redirect if the page has moved since the snapshot, and is rolled again if it no longer exists. Start and target, plus the checkpoints (`via0`…`via2`, as many as `viaKeys()` gives) under the Checkpoint rule, are rolled in parallel. `cardKeys()` lists the cards in use, in the order they are played, and `reroll('all')` rolls those and drops checkpoints not in use. `rollOne` reads the other cards after each await, so they normally don't land on the same article. If they do, `updatePlay` disables Start.
- *Pools* (the Pool row; RESEARCH.md has the testing behind them). Each card draws a group, then a member of it. `rollGroups` gives the groups: the five topics, then each family or spin-off that is on as one more group. It keeps them per pool, Content and whether the card needs links (`linked`, for a target or checkpoint, keeps only titles linked from at least `MIN_BACKLINKS` articles outside navboxes). `planGroups` picks a different group for each card, uniformly, so the start and target are never from the same topic (a topic's navbox would put them one click apart), and gives the target the chosen topic first. `groupOf` reads a card's group from its page, which also covers custom, challenge-link and daily cards. A custom article may be anything.
  - *Popular*: the best-linked 30% of the pool (`tiers` has `popular`), from Lava, Fire and Villager down to about Andesite and Deep Dark. It is the relaxed pool: its pairs have the most routes.
  - *Everyday*, the default: the whole pool.
  - *Deep cuts*: the least-linked third of each topic, among articles linked well enough to be a target (`deep`), such as Camel Husk or Curse of Binding. Mobs are all well known, so a few are in Popular too.
  - The topics are uneven (blocks 478, items 273, mobs 93, world 94, magic 82), so drawing a topic first gives each a fifth of the rolls. A family or spin-off that is on is one more group, so Dungeons (1,364 pages) gets the same share as a topic.
- *Chaos*: uniform over `CHAOS_TITLES`, every article with no exceptions (version pages, render-history subpages, disambiguation and non-content pages included), plus every page of each spin-off that is on (`SPINOFF_PAGES`). Its cards may share a topic. Its targets and checkpoints come from the half linked from at least `MIN_BACKLINKS` articles outside navboxes, since nothing could reach the rest.
- *Content* is the Content row (the families) and the Spin-offs row, with All (`syncAllSpinoffs` ticks it when every spin-off is on and shows a dash when only some are). In Chaos the families are in anyway, so `syncContentToMode` shows their boxes ticked and disabled, and gives back what they were on leaving Chaos. `init` runs it too, since a reload can bring the Pool radio button back on Chaos. Changing Content rerolls every card, as changing the pool does, which leaves a daily. `loadDaily` turns all Content off (`setContent([])`), since a daily is its pair and rule only.
- *Target topic* (`TOPICS`, the select in the Target row) pins the target's group to that topic in every pool, Chaos included (there it draws from the whole topic). A new topic rerolls the target, and in the pool modes the start too if it is from that topic. `rollOne` stamps a rolled target with `topic`, and `finish` copies it into the record. Targets that weren't rolled as targets (custom, challenge link, daily, swapped in) have none. The topic isn't carried in challenge links, since the link already fixes the pair.
- *Target par* (`REACHES`, `reach()`, the Target row's second select, hidden under Scavenger): Any par, Par 1 or Par 3+, how many clicks the target is from the start under the difficulty and Content. Almost every pool pair is par 2 and none is 4 or more (on the 2026-08 snapshot, par 3 is 4% of targets in Normal and 17% in Hard, and in Relaxed only a quarter of starts have a par 3 target), so these are the one-click targets and the far ones. With a par chosen, `reroll` rolls the start and target after the other cards: `distancesFrom` searches the link graph from a start, and `rollOne`'s `accept` takes a start only if some target is at the par from it (giving up after `PAR_STARTS` starts, and saying so), then draws the target from those at the par (`titles`), both before any lookup. Drawing the target at random instead would miss: in Relaxed a start may have one or two par 3 targets among a thousand. Unless a topic is chosen the target may then come from any topic but the start's (`candidates`), since some topics have no far targets from most starts. Rerolling only the target says so if the start has none. Like the topic, it is stamped on a rolled target (`reach`), shown in the settings text unless Any, and not carried in challenge links. It is recorded only if the game's par still fits it, since a new start or difficulty can move the pair off it.
- A target or checkpoint must be linked from at least `MIN_BACKLINKS` articles outside navboxes (`body`), so No navboxes never gets one that only navboxes link to, and all cards must differ. The topic applies only to the target.
- *Daily* (`loadDaily`, `dailyPair`): a local date fixes a pair and one rule. The pair comes from `POOL_TITLES`, whatever the pool and topic, with the target (and the checkpoints) from a topic no card before it has, so a new `wiki-data.js` can change past days' pairs. Every title is ranked by `hash32("date|start|title")` (or `|target|`), and the lowest-ranked one that passes the usual checks wins. With rendezvous hashing like this, pages joining or leaving the categories only change a day's pair if they would rank first, which re-indexing a sorted list would not give. Every daily plays on Normal plus one rule (`dailyRule`), ranked the same way over `DAILY_RULES` (salt `rule`): No Back, Blind target, Checkpoint, No hubs (which makes it Hard), Six clicks, Round trip (a Race there and back), Exact clicks or Scavenger. An Exact clicks day only takes a target with a route of exactly its count (`exactRoute`, with no Content), and a Scavenger day ranks its mode over `DAILY_HUNTS` (salt `hunt`): kinds are the first in the day's ranking (salt `kind`) from three topics, none holding the start, and articles are the target and two more taken like checkpoints, needing a route in any order. A kinds daily has no target, so `init` checks `cardsLoaded()`, not the target, before rolling a pair instead. A daily can always be done: `dailyPair` only takes a target (and each checkpoint, after the ones before it) where the link graph has a route under the day's rules, and on a Six clicks day one of `DAILY_SIX_CLICKS_PAR` (4) clicks or fewer, leaving two for a wrong turn. That check comes before each lookup, so it costs no requests, but the daily needs the graph and fails to load without it. On a Checkpoint day `dailyPair` also ranks the count over `DAILY_CHECKPOINTS` (1 or 2, salt `checkpoints`: three would use every topic and make a long daily) and picks the checkpoints (salts `via`, `via1`). `loadDaily` replaces the ticked rules with the day's. `setup.daily` holds the date while the cards and rules are the day's, and any reroll, custom article, swap or rule change clears it (`leaveDaily`) and shows the same notice (`LEFT_DAILY`), so a daily always means that pair with that rule. The game copies it to `game.daily`, and the record stores it as `daily`.

**Par and Golf.** Par is the fewest clicks for a pair, going by the snapshot. The setup screen shows it beside Start (`updateSetupPar`, run from every `renderCard`, so the first card rendered starts loading the graph and it is ready by the time a game starts), `startGame` works it out for the game (`game.parReady`, then `game.par`, which the header shows), and the result scores a win against it as golf does, each name with what it means for anyone who doesn't play golf (`golfScore` gives `{ name, note, over }`: Hole in one! (par 1 in one click), Par (even with par), Bogey (1 over par), Double bogey, Triple bogey, then just "N over par"; Birdie and Eagle only where the live wiki has a link the snapshot hasn't; `golfText` writes it in one line for the copied result) and shows one shortest route (`showPar` fills the score badge `#mScore`, orange when over par, the Par tile, the shortest route column `#mBest` and the wiki-date line `#par` once it knows, unless that result has been closed).

**The result window** (`finish`, `.result`) goes: the outcome as the heading (a loss in the target colour, with its reason under it) and the golf score beside it; the game and its extra rules as labels, like the header's, with the route and the settings the labels don't say; four tiles (clicks, or "2 of 4" for Exact clicks, par, time, time per click); the personal best (a green bar when it is a new one); your path, each page marked with what it was (back, a checkpoint, a find, the target, Hot/cold's hint), beside the shortest route (for Exact clicks, a route of its count); then Copy result, Retry this pair and New game. On a narrow screen the tiles go two across and New game takes the full width above the others. The record keeps `par`, added afterwards to a record saved before it was known, and the history and copied result show it. `parRoute` loads the graph the game was played on (`linkGraph`: `wiki-links.js`, and `wiki-navboxes.js` for Relaxed, each the first time it is needed, refused if its sha256 isn't `WIKI_DATA`'s) and searches it breadth-first (`shortestRoute`), opening each navbox once, the first and nearest time it is reached. It follows the game's settings: navbox links only count in Relaxed, hubs are dead in Hard but the target's and the checkpoints' (`routeUsable`), a spin-off's pages only count when it is on, and the checkpoints split the route into legs (`legsRoute`). A round trip is the way there plus the way back, each through its own checkpoints (`roundTripRoute`). The way back can't use a page of the way there but the stops still ahead, which makes the fewest clicks a shortest loop through given pages, NP-hard in general, so it tries the shortest way there with the shortest way back around it and the other way about, then again with each page of those banned in turn (up to `ROUND_TRIP_TRIES`), stopping at the lower bound, the shortest way there plus the shortest way back. On this snapshot it reached that bound in all of 898 pairs tried in Normal, Relaxed and Hard and all of 398 with a checkpoint each way, so par is exact in practice. Scavenger's par is exact too: for articles the shortest over every order (`huntRoute`, `orders`), since revisits are allowed, and for kinds a breadth-first search over (page, kinds found) (`kindsRoute`), which goes by the snapshot's members only, so a live-only find can beat it. With Round trip each goes home from its last find around the hunt: articles through `roundTripRoute` for each order, the orders taken by their lower bound, and kinds from each finished hunt in turn, nearest first, skipping those whose shortest way home at all (`distancesTo`) can't win, so these two are no longer exact. Live edits since the snapshot can make the real fewest clicks lower or higher, so the line names the snapshot's date. It also shows one route that takes that many.

**Rendering articles.** Each article is written into a sandboxed iframe (`sandbox="allow-scripts"`, so it gets an opaque origin) via `srcdoc`. This design is deliberate:
- The wiki's own stylesheets (`WIKI_STYLES`, loaded from `load.php`) apply without leaking into the game UI. They rely on `:root` and `body.wgl-theme-*` selectors, which is why a shadow root doesn't work.
- `<base href="https://minecraft.wiki/">` resolves the parse output's relative `/images/...` URLs, `srcset` values and CSS `url()` values without any rewriting.
- Values written into the frame's script go in as JSON with `<` escaped, since a link fragment can hold any text and an HTML comment opener followed by a script tag would make the parser run past the closing tag. That sequence must not appear literally anywhere in `index.html`'s scripts either, comments included: the page would silently not run.
- An inline script inside the iframe classifies every `<a>` and image-map `<area>` and intercepts clicks. Same-page `#anchors` scroll locally. Main-namespace `/w/Title#frag` links are sent to the parent with `postMessage({mwr:'nav', title, frag})`. Live links get `mwr-live`, which gives them a focus ring and tints text links (not ones around an image) in their own colour on hover. Links to an article already visited this game also get `mwr-seen`: a visited-link purple with a dotted underline, or a dotted outline around an image, since the browser can't track visits inside the frame. `game.seen` maps every visited title, and the link title that led there, to the article. `navigate` passes its keys to `renderArticle` as `seen`, leaving out everything still ahead (a target or checkpoint passed early still has to be reached). Other redirects to a visited article aren't known, so their links aren't marked. The frame capitalises a link's first letter as MediaWiki does, so its titles match the `seen` and `blocked` lists. Everything else gets the `mwr-dead` class (dimmed) and does nothing: other namespaces (`NAMESPACES`, including `Tutorial:`, `File:` and `Category:`, and a spin-off's unless it is in `game.content`), red links (`.new`), external links and `?query` links. Titles passed in `blocked` (No hubs) are dead too, and under No navboxes so is every link inside a `.navbox` table. Those tables and their Navigation heading are also hidden.
- A script at the top of the iframe's `<head>`, ahead of the stylesheets, loads a failed image once more after 2 s. If it fails again it gets `mwr-broken`, which keeps the image's box and hides its alt text: on inventory icons the alt is a whole sentence, which Firefox would draw running out of the 32 px slot and down the table.
- The frame script also runs the wiki's element animator (from MediaWiki:Common.js, which the frame doesn't load): every 2 s each `.animated` shows its next child (and an `.animated-subframe` child its own next child), so crafting grids cycle through their recipes instead of freezing on the frame the parse output marked (inside a subframe that is a different item per slot, such as a different plank in each). As on the wiki, an animation inside a `.mcui` or `.animated-container` holds still while the pointer or focus is in it, so the slot being aimed at can be clicked, each animation keeps the height of its tallest frame, and its hidden frames' images are made eager once it scrolls into view.
- It also runs the Tabber extension's script (its styles, `ext.Tabber`, are in `WIKI_STYLES`): each `.tabber` gets a row of tabs made from its panels' `data-title` and shows one panel at a time, starting on the one holding the linked section. Infoboxes use it for an item's variants (Wooden, Golden, Stone… on Pickaxe); without it every panel shows, one under another. It runs after the animator, which would measure frames in hidden panels as 0 px.
- And the wiki's layered blueprint gadget: each `.layered-blueprint-tab` (Layer 1, Layer 2… on a structure's blueprint) becomes a radio button and its label, and the wiki's CSS hides the layers above the checked one.
- The wiki's calculators (`.mcw-calc`) are hidden: its script replaces each with an iframe, and without it they only say they are loading.
- The article is drawn in the wiki's light or dark theme (`wgl-theme-light`/`wgl-theme-dark` on its `<body>`), matching the game theme (see Themes). `wgl.theme.dark` is always in `WIKI_STYLES` (about 4 KB gzipped): apart from a few rules that change nothing visible here, it is scoped to the dark body class, so switching is a swap of `WGL_THEME_CLASSES`, which the parent asks for with `postMessage({mwr:'theme', dark})` without reloading the article. The parent also sends it when the frame reports `ready`, which catches a theme change made while the article was loading.

**Game rules / state** (`game` object):
- `game.content` is the Content in play: what is on at `startGame`, plus the spin-off of any card's page (`spinoffOf`), whose links have to work to reach it, so a challenge link starting on `Dungeons:Creeper` needs no checkbox. `renderArticle` leaves its spin-offs out of the frame's dead namespaces. `toInfo` accepts a page in a spin-off's namespace by its number, taken from the ZIM's `ns-N` body classes, which match the live API's `ns`.
- *Difficulty* (`LEVELS`, the Difficulty row) is the rules No navboxes and No hubs: Relaxed has neither, Normal (the default) No navboxes, Hard both. The research behind it: with navboxes almost any sensible click gets closer (RESEARCH.md). The two rules stay rule keys, so `game.rules`, the frame, the personal-best key and challenge links treat them like any other rule, but the extra rules don't list them. `rules()` adds the difficulty's to the ticked ones, `setRules` sets the difficulty from them (`levelOf`), and `rulesText` names the difficulty unless it is Normal, so the Settings column shows "Hard" or "Relaxed".
- *Rules* are defined in `RULES`. The games' rules (Checkpoint, which the screen calls Relay, Scavenger, Exact clicks) can't be played together, so the game tiles pick one (`GAMES`, `gameMode()`; a Race has none), and the rest (`EXTRA_RULES`: Round trip, No Back, Blind target, Hot/cold, Six clicks) are checkboxes that go with any game but Exact clicks, which plays without Six clicks (it has its own count) and Round trip (it never visits a page twice): there those boxes are disabled and say why (`OFF_IN_EXACT`), and `rules()` leaves them out even if ticked. With Round trip on, each game's tile and strip say what it is then (`GAMES`' `trip`). All of these are `input.rule` checkboxes or the game radio, which `rules()` reads, and `setRules` sets the game from a set of rules with `gameOf` (a hand-made link with several games' rules plays the first of Exact clicks, Scavenger and Relay). `startGame` copies `rules()` into `game.rules` (sorted in `RULES` order), and everything during play and in `finish` reads that, never the checkboxes. Changing a rule or the difficulty doesn't reroll, but leaves a daily. *No Back* hides the Back button and is also enforced in `goBack()`. *No hubs* makes links to the hubs (`hubs` in `tools/wikidata/config.json`) dead: `HUB_TITLES` maps every hub and its redirects, those to sections included (about 1,000 titles, from `wiki-data.js`), to the hub, and `navigate` passes all of them except the target's hub to `renderArticle` as `blocked`. Going Back to a hub start is allowed, and a hub that is a checkpoint stays live too. *Blind target* keeps every card but the start, and Scavenger's kinds, off the setup screen (`hiddenKeys`): they stay empty until Start picks them (`pickHidden`, through `reroll(…, true)`, with a target par holding as usual and for Exact clicks a target with a route of its count, waiting on the latest `updateSetupPar` run, `setup.parRun`), or are held unseen when the game was fixed beforehand (the daily, a challenge link, and Copy challenge link, which picks them first since the link carries them; it still carries their titles plainly). Their cards say Hidden and when each shows (`shownWhen`: when the game starts, or in a Relay when the stop before it in playing order is reached, the target among the checkpoints on a round trip), with no Reroll or custom box, Swap is hidden, and par and Exact clicks's count wait for the game. Any reroll, a new start, and any rule or difficulty change while it is on or just turned off (`setup.blind`, set by `setRules` and the change listener) drops them (`dropHidden`), so turning it off rolls new ones rather than showing the held ones; `renderCard` and `renderKinds` read the checkbox, and changing any rule re-renders the cards. A target par under it rerolls the start too, since only a start with a target at that par will do. During play it hides the picture and description in the HUD, behind the path and through the peek button, which is hidden, and in a Relay `renderObjective` shows a stop ahead as ? until the one before it is reached, all but the start a round trip goes back to. Scavenger's finds all show from the start, since they go in any order. *Hot/cold* hints after each arrival but the first and the objective's own (a target or later checkpoint passed early gets one) whether the page is closer to `objective()` than the page before it (`hotColdHint`: the fewest clicks from each, by the link graph under the game's settings, `routeUsable`, as par uses; a page with no route counts as farthest, so a dead end is colder): Warmer, Colder, Same distance, or No hint for a page the snapshot lacks. It never says how close. The hint goes onto the path entry (`hint`, a marker in the path list) and shows over the article (`showHint`, from the arrival once the hint is known and from `frameReady`, whichever comes last, and only for the latest arrival). It isn't a daily rule, since it makes a game easier. *Six clicks* shows the count as "of 6" under the clicks, with a dot a click (`#hudClicksK`, `#hudMeter`, from `game.limit`), and `navigate` ends the game as lost (`finish(false, 'outOfClicks')`) when an arrival that isn't the target uses up the last click. *Exact clicks* is a game too, and takes Six clicks's place: the target has to be reached in exactly par + `EXACT_EXTRA` (2) clicks, on no page twice. Revisits are out because a page almost always links back to the one before, which would make any count easy. So Back is hidden (`canGoBack`), every visited page is dead by every title that led to it (`game.dead`, renewed on each arrival), and reaching the target sooner loses (`tooSoon`), as does using up the count (`game.limit`, `outOfClicks`). The count can always be done: `updateSetupPar` finds a route of exactly that many clicks (`exactRoute`, `setup.exact`) and Start waits for it. That is NP-hard in general, so `exactRoute` searches depth first through pages the target can still be reached from in the clicks left (`distancesTo`, a breadth-first search back from the target over reverse edges made once per graph file), the farthest first, and gives up after `EXACT_BUDGET` pages. On this snapshot it found one of par + 2 for every one of 447 pairs tried, in a few milliseconds. The result shows that route, and a win gets no golf score, since every win is par + 2. *Scavenger* (the Scavenger hunt game): instead of a target there are `HUNT_SIZE` (3) things to find, in any order, chosen with `#huntMode` in its strip. *Articles* (`huntMode() === 'articles'`) puts them on the two checkpoint cards and the target card, labelled Find and joined by +. *Kinds* puts three kinds (`KINDS`, from `wiki-data.js`) on a card of their own (`#cardHunt`, `setup.kinds`, `setKinds`), each with its best-known members as examples; `rollKinds` takes them from three topics, none holding the start (`firstKinds`, which the daily uses too), and a new start in one of them rolls them again (`renderCard`), since the start never counts. `startGame` puts them in `game.hunt` (`{ info }` or `{ kind }`, with a label), with `game.goal` null, so the code that reads the objective asks `game.hunt` first (`huntLeft`, `ahead`, `cardTitles`). An arrival finds (`huntFinds`) an article by its title and a kind by its snapshot members or the page's live categories (`parse.categories`, asked for with every article) less the kind's exclusions, so a page added to a category since the snapshot counts. A page can find several kinds at once. Each find gets the checkpoint's banner ("✓ Found a Nether mob: Blaze (2 of 3)") and its path entry `found`; finding all wins. Hot/cold aims at the nearest of what is left. Swap reverses the articles, and is hidden for kinds.
- *No navboxes* removes the navbox tables, which link most game content to the rest of its family (on Diamond, 1,984 live links drop to 829). Popular and Deep cuts rank articles by their links from outside navboxes, and every target is linked from at least `MIN_BACKLINKS` articles outside them. *Checkpoint* adds one to three cards between start and target (the count is `#viaCount`, in the Relay's strip; `syncVia` shows the cards in use, numbers them when there is more than one, and rolls the empty ones). A relay of two or three is the same rule. `game.vias` must be reached in order (`game.viaNext` counts them, set in `navigate` from the post-redirect title, with that path entry's `via` set to the checkpoint's number) before arriving at the target counts; a later one reached early is an ordinary page. The header's route and the picture behind the path follow `objective()`: the next checkpoint until all are reached, then the target. Reaching one sets `game.celebrate`, and once that article has rendered `frameReady` calls `celebrateCheckpoint()`: a banner over the article naming what comes next (`#toast`, gone after 3 s or on the next navigation) and a flash of the HUD objective. Swap reverses the whole chain. *Round trip* goes with any game but Exact clicks: whatever the game asks, then back to the start, which the setup screen marks with "Start and finish" (and a ⇄ arrow when nothing stands between). In a Relay the checkpoints go around the target: `setup.back` (`backCount()`) of them come after it, on the way back, rolled with the cards (`rollBack`: one checkpoint either side, of two or three at least one each way) and kept, or moved to the nearest that fits, when the count changes. `placeTarget` moves the target card among the checkpoint cards, with its own arrow (`#goalArrow`), and Swap goes round the same loop from the target instead: the start and target change places and the checkpoints of the way back come first. `startGame` plays a round trip as a chain with the target as one more checkpoint (`game.turn`, its number among `game.vias`) and the start as `game.goal` (`game.roundTrip`), so the objective, the banner, Hot/cold and the win check need little of their own; `viaName` and `checkpointNumber` number the checkpoints around the target. Scavenger's heads for the start once nothing is left to find (`hunting()`, which `objective()` is null during). `finish` records it by its cards: the target as `goal`, the checkpoints as `vias` and `back`. Reaching the target, or the last find (`turnBack`), starts the Back stack again from there, so Back can't walk the way there backwards, and makes every page of the way there dead, the target included, but those still ahead (`ahead()`: the checkpoints of the way back and the start): `game.dead` holds their titles and the link titles that led to them, which `navigate` adds to `blocked` and Hot/cold avoids. If the snapshot has no way on around them, that arrival gets the `stranded` hint, saying only giving up is left. The path entry is marked in the accent colour. `CLICK_LIMIT` covers the whole route.
- While a game is on (`startGame` until `finish` or `toSetup`), a `beforeunload` listener (`guardLeaving`) makes closing the tab, reloading, the browser's Back and any other way of leaving the page ask first with the browser's own dialog. It is added and removed rather than left on, since a page with one may be kept out of the back/forward cache. Browsers only show the dialog after a real click or key press, and a game only starts from one (Start or Retry this pair). iOS Safari doesn't show it at all.
- `path` records every visit in order and drives the click count (`path.length - 1`).
- `stack` is the navigation stack for Back. Going back is recorded in `path` and counts as a click.
- The win check compares `parse.title`, which is the title after redirects, against the target's resolved title. Following a redirect to the target therefore counts as arriving.
- The clock pauses while an article is loading and rendering, and while the Give-up confirmation is open. It keeps running while the player peeks at the target description. `game.loading` stays set until the frame posts `{mwr:'ready', token}`. That message comes from its own `<script>` after the main frame script, so it is sent only after the render-blocking stylesheets have loaded. A 15 s timeout calls `frameReady` anyway. An article that fails to load (a network or HTTP error, a MediaWiki error, a reply that isn't JSON or has no article) shows Retry and Cancel with the clock stopped. Everything that can fail has to fail inside `navigate`'s `try`: an error after it would leave the game loading, with Give up disabled.
- `navToken` throws away responses from navigations that have been superseded, and stale `ready` messages too.
- `parseCache` keeps up to `PARSE_CACHE_MAX` parse results, stored under both the requested and the resolved title, and is cleared on return to setup. Back and "Retry this pair" don't refetch. The API marks parse responses uncacheable, so the browser's HTTP cache can't do this.

**Themes.** A theme is the set of CSS variables on `:root` (colours, `--font`, `--radius*`) plus `color-scheme`, which also decides the article's wiki theme (`themeIsDark()` reads the computed `color-scheme`, falling back to `prefers-color-scheme` when it is ambiguous). Built in: Auto (no `data-theme` attribute, follows the OS), Light and Dark (`data-theme="light"`/`"dark"`). Auto's dark rule is `:root:not([data-theme])`, so no other theme ever picks up the dark variables. A page serving the game can add themes without editing this file: a `<link rel="stylesheet">` or `<style>` in `<head>` with `data-mwr-theme="Name"` that defines `:root[data-theme="Name"]`, plus `data-mwr-default` to make it the default. The names `auto`, `light` and `dark` belong to the built-ins (a host theme named `auto` could never apply). The `#theme-boot` script at the top of `<body>` runs before first paint: it builds `THEMES` (used by the main script) from those elements and applies the saved theme if it still exists, else the default, else Auto. It is not `<script>` followed by a newline on purpose, so the syntax-check regex still finds the main script. The picker on the setup screen calls `setTheme()`.

**Pictures.** Thumbnails are requested at 400 px (`pithumbsize`). Every setup card and the path sidebar also show a large faded copy (`.art`, at `--art-opacity`, which themes can set) behind their content and cut off by the box's edges: the card's article, and in the sidebar `objective()`. The sidebar's is hidden on narrow screens. Pictures are drawn with hard edges (`image-rendering: pixelated`), except ones whose URL has `/thumb/`: the wiki serves small sprites at their own size (Diamond is 160 px), so a thumbnail URL means it scaled down a bigger render or screenshot, and those are drawn smoothly. A `/thumb/` `.art` also gets a radial mask, which softens a screenshot's rectangular edges.

**Sounds.** Every sound is synthesized with Web Audio when it plays (`SOUNDS`, played through `play()`), so there are no sound files and nothing is fetched. They are original, in the spirit of note blocks and the XP orb, not copies of Minecraft's: a link click is a pling that climbs a pentatonic scale with each click of the game (played when the navigation starts, so a slow load doesn't delay it), Back falls two notes, a dead link thuds (the frame posts `{mwr:'dead'}`), the checkpoint chimes from `celebrateCheckpoint`, and `finish` plays a fanfare for a win, a longer one for a new personal best, a sad trombone for Six clicks and two falling notes for giving up. The `AudioContext` is made on the first sound, which always follows a click or key press, as browsers require, and any audio error is swallowed. Sound is on by default, muted with the Sound checkbox beside Theme or the speaker button in the game header (`setSound`).

**The game header** (`renderObjective`, redrawn when the objective changes) has the game and its extra rules as labels (`#hudTags`) with how far along it is ("1 of 2 checkpoints reached", "Found 1 of 3", "On the way back", Exact clicks's count), and Hot/cold's latest hint beside them (`#hudHint`, from `renderHud`, coloured warmer orange or colder blue by the `--warm`/`--cold` theme variables). Under them is the route (`#hudRoute`): every stop as a chip, done (✓, a button), now (the objective, holding `#hudImg`, `#hudLbl` and `#hudGoal`) or ahead (dashed), joined by arrows; for Scavenger the things to find, found ones ticked with what found them. A route of more than `ROUTE_FULL` (3) stops shrinks the done chips to their ✓ (their names stay in a tooltip), and a click on one opens them all (`.route.open`); the row scrolls sideways when it still doesn't fit, kept on the objective by `scrollRouteToNow` (also on resize). The ? button beside it is the peek. On the right are the clicks (with a limit, "of 6" or "of exactly 4" and a dot a click), par, time, sound, Back and Give up.

**Phones.** At 720 px and below the setup cards stack, Start game spans the width, and Recent games shows each game as a card (the labels and the day, the route, the result and time) instead of table columns. On a phone held upright (also taller than 500 px) the game header puts the labels and the route on their own rows above clicks, time and the buttons, Back shows only its arrow, and the path sidebar becomes one line of breadcrumbs that scrolls sideways, kept at its newest entry by `scrollPathToEnd` (also on resize, as turning the phone switches layouts), with a faded left edge while there is more to the left (`markPathScroll`), Hide beside it and the credit under it. Any screen 500 px tall or less, such as a phone on its side, keeps the sidebar at 160 px instead. On touch screens (`pointer: coarse`) inputs use 16 px text so iOS doesn't zoom on focus and the small controls are bigger. The game is `100dvh` tall so phone toolbars don't cover it. Inside the frame the article's padding narrows below 600 px, and the hover tint only applies with `(hover: hover)`, since on a touch screen it would stay on the tapped link. The wiki's own CSS already makes wide tables scroll sideways.

**Persistence.** `localStorage` key `mwr.history` holds the last 50 results and is used for the recent-games table and the per-pair personal best. Storage is shared with every page on the origin and open to the player, so it is read through `savedGames()`, which leaves out anything `isRecord` doesn't accept as a record `finish` would write (the wrong types, or a rule, topic or Content key that doesn't exist). A Scavenger record has `finds` (its articles) or `kinds` (their categories) in place of `goal` (`isRecord` takes exactly one of the three, and `targetText` and `routeText` say them), and `recordKey` keys its personal best with its finds in any order. A lost record has the flag of its `LOSSES` key, `outOfClicks: true` (Six clicks or Exact clicks) or `tooSoon: true` (Exact clicks), an Exact clicks game has `exact` (its count), and a Checkpoint game has `vias` (the checkpoints' titles, in order), with `back` on a round trip when some come after the target. The whole `chain` (start, checkpoints, target, the checkpoints of the way back, and the start again for a round trip) and the rules are the personal-best key. Each record has `rules` (an array of rule keys), and the personal best only compares records with the same rules (`sameRules`). A rolled target's `topic` and `reach` are recorded too, and so is `game.content` as `content` when anything was on, and `par` once known (none of them part of the personal-best key, since the cards already fix the game; `isRecord` only accepts `TOPICS` and `CONTENT` keys and a whole number for `par`). The result note shows the topic when it isn't Any and the Content as "Content: April Fools, Dungeons" (`settingsText`). Recent games (`renderHistory`) has five columns: the game as labels like the header's (the game, its extra rules, and a daily's day as a green "Daily 20 Oct"), the route (`routeText`) with the settings the labels don't say under it, the result (a badge, green for a win, orange for a loss, grey for giving up, with the golf name and par, or "Par 2" at par, under it, and Best on each pair's personal best), the time and the day (`whenText`: Today, Yesterday, then `shortDate`). The Clear history link above the table empties it, dailies included, after a confirmation dialog. `mwr.theme` holds the chosen theme, `mwr.sound` whether sound is on, and `mwr.pathCollapsed` whether the path sidebar is collapsed (`setPathCollapsed`). Access goes through the `store` wrapper, which swallows storage errors.
