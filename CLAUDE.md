# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

MC Wiki Race, a wiki race (like thewikigame.com) through minecraft.wiki: the player gets a random start and target article and must reach the target by clicking links inside articles, scored on clicks and time. The whole game is one `index.html` with no build step and no dependencies, plus `wiki-data.js`, which it loads with a script tag and which is generated from an offline copy of the wiki (see Wiki data). Beside them are only static assets: the icon (`favicon.ico` at 16/32/48 px, `apple-touch-icon.png` at 180 px) and the 1200×630 link-preview image `og-image.png`. The name follows Mojang's usage guidelines, which forbid "Minecraft" as the first word or dominant part of a fan project's name. Its home is https://mcwikirace.com/ (BryantF.xyz/games/mc-wiki-race forwards there), and `<head>` has a meta description, Open Graph tags and a `canonical` link pointing there, so every copy of the page names that address as the original. The footer says who runs the game (BryantF.xyz, linked) and how to reach them, which the guidelines also ask for. Articles, pictures and descriptions are fetched live from the minecraft.wiki MediaWiki API at runtime, while what rolls pick from (the pool, link counts, hub redirects, namespaces) comes from `wiki-data.js`.

## Running

Open `index.html` directly in a browser (`file://` works; no server needed). `python3 -m http.server` also works if a real origin is wanted.

The setup screen ends with a footer (who runs it and a contact address, GitHub link, MIT license, credit for the wiki's CC BY-NC-SA 3.0 content, a non-affiliation notice). That licence asks reusers to link the pages they show, so during play the bottom of the path sidebar (`#credit`, set in `navigate`) links the current article on minecraft.wiki (`wikiUrl`) and the licence (collapsing the sidebar leaves it in a small box over the article's corner, with the button that brings the sidebar back), and the result dialog links every page in the path. Without JavaScript, a `<noscript>` style in `<head>` hides the setup controls and a `<noscript>` notice under the intro explains why.

A `#start=<Title>&target=<Title>` URL hash loads a fixed pair (this is what "Copy challenge link" produces), which is handy for testing a specific route. `#daily` loads today's daily pair and rule, and `#daily=YYYY-MM-DD` any past day's. A date that doesn't exist or hasn't come yet (by the player's local date, `dailyDate`) loads today's instead, so nobody can practise a daily before its day. An optional `&rules=noback` (comma-separated rule keys) sets the rule checkboxes; it is applied even if the pair fails to load, and a daily replaces it with the day's rule. `&via=<Title>` adds a checkpoint and turns the Checkpoint rule on.

## Wiki data

`wiki-data.js` is generated from the English Kiwix ZIM of minecraft.wiki, which is linked from [Minecraft Wiki:Offline use](https://minecraft.wiki/w/Minecraft_Wiki:Offline_use) and rebuilt quarterly. Don't edit it by hand. The ZIM (1.9 GB) is downloaded by hand from `https://download.kiwix.org/zim/other/` into the repo root. `.gitignore` keeps it out of git and only its checksum is committed (`sha256sum -c minecraft.wiki_en_all_2026-08.zim.sha256`). The tools in `tools/wikidata/` are Python, run in an ignored venv (`python3 -m venv .venv && .venv/bin/pip install -r tools/wikidata/requirements.txt`), always with `.venv/bin/python -I`:
- `extract.py <zim>` scans the ZIM (about a minute) into an ignored snapshot, `tools/wikidata/cache/<name>.jsonl.gz`. It holds every page's namespace (from mwoffliner's `ns-N` body class, since main-namespace titles can contain colons), visible categories and links. Links are split into those outside and inside `.navbox` tables (nested tables count as inside), taken from the parser output only, and resolved against the page's own path as a browser would, since a subpage links to `../Diamond`. Redirects include mwoffliner's forwarding pages for redirects to a section.
- `build.py <snapshot>` writes `wiki-data.js` from the snapshot and `config.json`, which holds the hand-picked inputs: the topics (each a list of categories; an article goes to the first it is in), the categories and titles that aren't game content (other editions, list and set index pages), the Popular and Deep cuts shares, the Content families by category (`joke`, `removed`, `education`, `fiction`, `variants`, `mechanics`; the pool leaves their articles out), the spin-off namespaces, the disambiguation categories, the hubs and the core namespaces the ZIM doesn't hold. Every article and every spin-off page is listed. A pool-mode roll may only pick content: not a subpage, a disambiguation page, a version page (in a category ending in "versions") or a page that isn't game content. Such content gets its topic, or its family or spin-off instead, and the pool's articles get their tiers: Popular is the best-linked share of the pool, Deep cuts the least-linked share of each topic among articles linked well enough to be a target (`tiers` in `build.py`, which `report.py` also uses). Education is its four exact categories (blocks, items, entities, mobs), since the broad Minecraft Education category also holds Brewing, Charcoal and Dye. Links are counted per linking page, through redirects: an article's count only has links from articles, and a spin-off page's also has links from its own namespace, which are live when that spin-off is on. The same snapshot always gives the same bytes, one entry per line, so a new snapshot reads as a git diff.
- `report.py <snapshot>` writes a Markdown report (about 3 minutes): pool sizes, what moved to a Content family, each family's and spin-off's size and possible targets, link-count quartiles, dead ends (articles with no route to the most linked one, so a game starting there can't be won), the pool designs compared, and hub candidates. The pool designs come from `config.json`'s `research` section (topics, categories that aren't game content, variant groups, Famous and Deep cuts shares), which only the report reads. Each design is measured on random pairs (`--pairs`, 200 by default, seeded by its name) with all links, without navboxes, and without navboxes or hubs: fewest clicks, good first clicks (links on the start page that begin a shortest route), the sweet spot and how familiar the ends are. `RESEARCH.md` records what the first run found.
- `diff.py <old> <new>` compares two `wiki-data.js` files, such as `<(git show HEAD:wiki-data.js) wiki-data.js`: pages added and removed, pool, family and spin-off members that joined or left, link counts that moved, and hub and namespace changes.
- `test.py` writes a small ZIM in mwoffliner's shape and checks the other tools against it, in a few seconds.

To update: download the new ZIM, replace the `.sha256` file, run extract, build, diff and the test, play a few games, and commit `wiki-data.js` with the checksum.

## Architecture (all in `index.html`)

**API access.** Every request goes through `api()`, which always adds `origin=*`, allows at most `API_CONCURRENCY` (4) requests in flight with the rest queued in order (MediaWiki asks clients not to send many requests at once), and times each one out after 30 s. That parameter is mandatory: it is what makes MediaWiki send `Access-Control-Allow-Origin: *` for anonymous requests, and without it the page cannot fetch anything from `file://`. Calls used: `prop=pageprops|pageimages|extracts` (`pageInfo`: disambiguation flag, thumbnail, redirect resolution, and the description: the first paragraph of the TextExtracts plain-text intro, since `pageprops.description` is often an infobox caption and keeps HTML entities) and `action=parse` (article HTML). Nothing polls; every request comes from a player action, and a roll makes one request.

**Picking articles.** Rolls draw titles from `wiki-data.js` (see Wiki data), which defines `WIKI_DATA`. `ARTICLES` maps every article and every spin-off page (titled `Dungeons:…`) to `{ links, body, topic, fams, tiers }`: how many pages link to it, how many of those from outside navboxes, its topic if it is in the pool, its Content (a family key such as `joke`, or its spin-off's name) and its tiers (`popular`, `deep`). Subpages, disambiguation, version and other non-content pages have neither topic nor Content, so only Chaos rolls them. `POOL` maps each topic (`TOPICS` holds their labels) to its articles and `POOL_TITLES` is their union. `CONTENT` maps each family key (`FAMILIES` holds their labels) and then each spin-off (`SPINOFFS`, name to namespace number) to the pages it adds, and `content()` lists the ones that are on, in that order. A rolled title is then looked up live with `pageInfo` for its description and picture, which also follows a redirect if the page has moved since the snapshot, and is rolled again if it no longer exists. Start and target, plus the checkpoint (`via`) under the Checkpoint rule, are rolled in parallel. `cardKeys()` lists the cards in use, and `reroll('all')` rolls those. `rollOne` reads the other cards after each await, so they normally don't land on the same article. If they do, `updatePlay` disables Start.
- *Pools* (the Pool row; RESEARCH.md has the testing behind them). Each card draws a group, then a member of it. `rollGroups` gives the groups: the five topics, then each family or spin-off that is on as one more group. It keeps them per pool, Content and whether the card needs links (`linked`, for a target or checkpoint, keeps only titles linked from at least `MIN_BACKLINKS` articles outside navboxes). `planGroups` picks a different group for each card, uniformly, so the start and target are never from the same topic (a topic's navbox would put them one click apart), and gives the target the chosen topic first. `groupOf` reads a card's group from its page, which also covers custom, challenge-link and daily cards. A custom article may be anything.
  - *Popular*: the best-linked 30% of the pool (`tiers` has `popular`), from Lava, Fire and Villager down to about Andesite and Deep Dark. It is the relaxed pool: its pairs have the most routes.
  - *Everyday*, the default: the whole pool.
  - *Deep cuts*: the least-linked third of each topic, among articles linked well enough to be a target (`deep`), such as Camel Husk or Curse of Binding. Mobs are all well known, so a few are in Popular too.
  - The topics are uneven (blocks 478, items 273, mobs 93, world 94, magic 82), so drawing a topic first gives each a fifth of the rolls. A family or spin-off that is on is one more group, so Dungeons (1,364 pages) gets the same share as a topic.
- *Chaos*: uniform over `CHAOS_TITLES`, every article with no exceptions (version pages, render-history subpages, disambiguation and non-content pages included), plus every page of each spin-off that is on (`SPINOFF_PAGES`). Its cards may share a topic. Its targets and checkpoints come from the half linked from at least `MIN_BACKLINKS` articles outside navboxes, since nothing could reach the rest.
- *Content* is the Content row (the families) and the Spin-offs row, with All (`syncAllSpinoffs` ticks it when every spin-off is on and shows a dash when only some are). In Chaos the families are in anyway, so `syncContentToMode` shows their boxes ticked and disabled, and gives back what they were on leaving Chaos. `init` runs it too, since a reload can bring the Pool radio button back on Chaos. Changing Content rerolls every card, as changing the pool does, which leaves a daily. `loadDaily` turns all Content off (`setContent([])`), since a daily is its pair and rule only.
- *Target topic* (`TOPICS`, the select in the Target row) pins the target's group to that topic in every pool, Chaos included (there it draws from the whole topic). A new topic rerolls the target, and in the pool modes the start too if it is from that topic. `rollOne` stamps a rolled target with `topic`, and `finish` copies it into the record. Targets that weren't rolled as targets (custom, challenge link, daily, swapped in) have none. The topic isn't carried in challenge links, since the link already fixes the pair.
- A target or checkpoint must be linked from at least `MIN_BACKLINKS` articles outside navboxes (`body`), so No navboxes never gets one that only navboxes link to, and all cards must differ. The topic applies only to the target.
- *Daily* (`loadDaily`, `dailyPair`): a local date fixes a pair and one rule. The pair comes from `POOL_TITLES`, whatever the pool and topic, with the target (and the checkpoint) from a topic no card before it has, so a new `wiki-data.js` can change past days' pairs. Every title is ranked by `hash32("date|start|title")` (or `|target|`), and the lowest-ranked one that passes the usual checks wins. With rendezvous hashing like this, pages joining or leaving the categories only change a day's pair if they would rank first, which re-indexing a sorted list would not give. The rule (`dailyRule`) is ranked the same way over `DAILY_RULES` (salt `rule`): every rule except Six clicks, the only one you can lose by, since nothing checks that a daily pair can be done in six clicks. On a Checkpoint day `dailyPair` also picks the checkpoint (salt `via`). `loadDaily` replaces the ticked rules with the day's. `setup.daily` holds the date while the cards and rules are the day's, and any reroll, custom article, swap or rule change clears it (`leaveDaily`) and shows the same notice (`LEFT_DAILY`), so a daily always means that pair with that rule. The game copies it to `game.daily`, and the record stores it as `daily`.

**Rendering articles.** Each article is written into a sandboxed iframe (`sandbox="allow-scripts"`, so it gets an opaque origin) via `srcdoc`. This design is deliberate:
- The wiki's own stylesheets (`WIKI_STYLES`, loaded from `load.php`) apply without leaking into the game UI. They rely on `:root` and `body.wgl-theme-*` selectors, which is why a shadow root doesn't work.
- `<base href="https://minecraft.wiki/">` resolves the parse output's relative `/images/...` URLs, `srcset` values and CSS `url()` values without any rewriting.
- Values written into the frame's script go in as JSON with `<` escaped, since a link fragment can hold any text and an HTML comment opener followed by a script tag would make the parser run past the closing tag. That sequence must not appear literally anywhere in `index.html`'s scripts either, comments included: the page would silently not run.
- An inline script inside the iframe classifies every `<a>` and image-map `<area>` and intercepts clicks. Same-page `#anchors` scroll locally. Main-namespace `/w/Title#frag` links are sent to the parent with `postMessage({mwr:'nav', title, frag})`. Live links get `mwr-live`, which gives them a focus ring and tints text links (not ones around an image) in their own colour on hover. Links to an article already visited this game also get `mwr-seen`: a visited-link purple with a dotted underline, or a dotted outline around an image, since the browser can't track visits inside the frame. `game.seen` maps every visited title, and the link title that led there, to the article. `navigate` passes its keys to `renderArticle` as `seen`, leaving out the current objective (a target passed before the checkpoint still has to be reached). Other redirects to a visited article aren't known, so their links aren't marked. The frame capitalises a link's first letter as MediaWiki does, so its titles match the `seen` and `blocked` lists. Everything else gets the `mwr-dead` class (dimmed) and does nothing: other namespaces (`NAMESPACES`, including `Tutorial:`, `File:` and `Category:`, and a spin-off's unless it is in `game.content`), red links (`.new`), external links and `?query` links. Titles passed in `blocked` (No hubs) are dead too, and under No navboxes so is every link inside a `.navbox` table. Those tables and their Navigation heading are also hidden.
- A script at the top of the iframe's `<head>`, ahead of the stylesheets, loads a failed image once more after 2 s. If it fails again it gets `mwr-broken`, which keeps the image's box and hides its alt text: on inventory icons the alt is a whole sentence, which Firefox would draw running out of the 32 px slot and down the table.
- The frame script also runs the wiki's element animator (from MediaWiki:Common.js, which the frame doesn't load): every 2 s each `.animated` shows its next child (and an `.animated-subframe` child its own next child), so crafting grids cycle through their recipes instead of freezing on the frame the parse output marked (inside a subframe that is a different item per slot, such as a different plank in each). As on the wiki, an animation inside a `.mcui` or `.animated-container` holds still while the pointer or focus is in it, so the slot being aimed at can be clicked, each animation keeps the height of its tallest frame, and its hidden frames' images are made eager once it scrolls into view.
- It also runs the Tabber extension's script (its styles, `ext.Tabber`, are in `WIKI_STYLES`): each `.tabber` gets a row of tabs made from its panels' `data-title` and shows one panel at a time, starting on the one holding the linked section. Infoboxes use it for an item's variants (Wooden, Golden, Stone… on Pickaxe); without it every panel shows, one under another. It runs after the animator, which would measure frames in hidden panels as 0 px.
- And the wiki's layered blueprint gadget: each `.layered-blueprint-tab` (Layer 1, Layer 2… on a structure's blueprint) becomes a radio button and its label, and the wiki's CSS hides the layers above the checked one.
- The wiki's calculators (`.mcw-calc`) are hidden: its script replaces each with an iframe, and without it they only say they are loading.
- The article is drawn in the wiki's light or dark theme (`wgl-theme-light`/`wgl-theme-dark` on its `<body>`), matching the game theme (see Themes). `wgl.theme.dark` is always in `WIKI_STYLES` (about 4 KB gzipped): apart from a few rules that change nothing visible here, it is scoped to the dark body class, so switching is a swap of `WGL_THEME_CLASSES`, which the parent asks for with `postMessage({mwr:'theme', dark})` without reloading the article. The parent also sends it when the frame reports `ready`, which catches a theme change made while the article was loading.

**Game rules / state** (`game` object):
- `game.content` is the Content in play: what is on at `startGame`, plus the spin-off of any card's page (`spinoffOf`), whose links have to work to reach it, so a challenge link starting on `Dungeons:Creeper` needs no checkbox. `renderArticle` leaves its spin-offs out of the frame's dead namespaces. `toInfo` accepts a page in a spin-off's namespace by its number, taken from the ZIM's `ns-N` body classes, which match the live API's `ns`.
- *Rules* are optional toggles defined in `RULES` and rendered as checkboxes under the modes. `startGame` copies the checked keys into `game.rules` (sorted in `RULES` order), and everything during play and in `finish` reads that, never the checkboxes. Changing a rule doesn't reroll. *No Back* hides the Back button and is also enforced in `goBack()`. *No hubs* makes links to the hubs (`hubs` in `tools/wikidata/config.json`) dead: `HUB_TITLES` maps every hub and its redirects, those to sections included (about 1,000 titles, from `wiki-data.js`), to the hub, and `navigate` passes all of them except the target's hub to `renderArticle` as `blocked`. Going Back to a hub start is allowed, and a hub that is the checkpoint stays live too. *Blind target* hides the target's picture and description: on the setup card (`renderCard` reads the checkbox, and changing any rule re-renders the target card), in the HUD, behind the path and through the peek button, which is hidden. *Six clicks* shows `clicks/CLICK_LIMIT` in the HUD, and `navigate` ends the game as lost (`finish(false, true)`) when an arrival that isn't the target uses up the last click.
- *No navboxes* removes the navbox tables, which link most game content to the rest of its family (on Diamond, 1,984 live links drop to 829). Easy and Hard still rank targets by all their links, navboxes included, but every target is linked from at least `MIN_BACKLINKS` articles outside them. *Checkpoint* adds a third card (`setup.via`, shown by `syncVia` while the rule is on). `game.via` must be reached (`game.viaReached`, set in `navigate` from the post-redirect title, with that path entry flagged `via`) before arriving at the target counts. The HUD label, name, picture, the picture behind the path and the peek show `objective()`: the checkpoint until it is reached, then the target. Reaching it sets `game.celebrate`, and once that article has rendered `frameReady` calls `celebrateCheckpoint()`: a banner over the article (`#toast`, gone after 3 s or on the next navigation) and a flash of the HUD objective. The path entry is marked in the accent colour. `CLICK_LIMIT` covers the whole route.
- While a game is on (`startGame` until `finish` or `toSetup`), a `beforeunload` listener (`guardLeaving`) makes closing the tab, reloading, the browser's Back and any other way of leaving the page ask first with the browser's own dialog. It is added and removed rather than left on, since a page with one may be kept out of the back/forward cache. Browsers only show the dialog after a real click or key press, and a game only starts from one (Start or Retry this pair). iOS Safari doesn't show it at all.
- `path` records every visit in order and drives the click count (`path.length - 1`).
- `stack` is the navigation stack for Back. Going back is recorded in `path` and counts as a click.
- The win check compares `parse.title`, which is the title after redirects, against the target's resolved title. Following a redirect to the target therefore counts as arriving.
- The clock pauses while an article is loading and rendering, and while the Give-up confirmation is open. It keeps running while the player peeks at the target description. `game.loading` stays set until the frame posts `{mwr:'ready', token}`. That message comes from its own `<script>` after the main frame script, so it is sent only after the render-blocking stylesheets have loaded. A 15 s timeout calls `frameReady` anyway. An article that fails to load (a network or HTTP error, a MediaWiki error, a reply that isn't JSON or has no article) shows Retry and Cancel with the clock stopped. Everything that can fail has to fail inside `navigate`'s `try`: an error after it would leave the game loading, with Give up disabled.
- `navToken` throws away responses from navigations that have been superseded, and stale `ready` messages too.
- `parseCache` keeps up to `PARSE_CACHE_MAX` parse results, stored under both the requested and the resolved title, and is cleared on return to setup. Back and "Retry this pair" don't refetch. The API marks parse responses uncacheable, so the browser's HTTP cache can't do this.

**Themes.** A theme is the set of CSS variables on `:root` (colours, `--font`, `--radius*`) plus `color-scheme`, which also decides the article's wiki theme (`themeIsDark()` reads the computed `color-scheme`, falling back to `prefers-color-scheme` when it is ambiguous). Built in: Auto (no `data-theme` attribute, follows the OS), Light and Dark (`data-theme="light"`/`"dark"`). Auto's dark rule is `:root:not([data-theme])`, so no other theme ever picks up the dark variables. A page serving the game can add themes without editing this file: a `<link rel="stylesheet">` or `<style>` in `<head>` with `data-mwr-theme="Name"` that defines `:root[data-theme="Name"]`, plus `data-mwr-default` to make it the default. The names `auto`, `light` and `dark` belong to the built-ins (a host theme named `auto` could never apply). The `#theme-boot` script at the top of `<body>` runs before first paint: it builds `THEMES` (used by the main script) from those elements and applies the saved theme if it still exists, else the default, else Auto. It is not `<script>` followed by a newline on purpose, so the syntax-check regex still finds the main script. The picker on the setup screen calls `setTheme()`.

**Pictures.** Thumbnails are requested at 400 px (`pithumbsize`). Every setup card and the path sidebar also show a large faded copy (`.art`, at `--art-opacity`, which themes can set) behind their content and cut off by the box's edges: the card's article, and in the sidebar `objective()`. The sidebar's is hidden on narrow screens. Pictures are drawn with hard edges (`image-rendering: pixelated`), except ones whose URL has `/thumb/`: the wiki serves small sprites at their own size (Diamond is 160 px), so a thumbnail URL means it scaled down a bigger render or screenshot, and those are drawn smoothly. A `/thumb/` `.art` also gets a radial mask, which softens a screenshot's rectangular edges.

**Sounds.** Every sound is synthesized with Web Audio when it plays (`SOUNDS`, played through `play()`), so there are no sound files and nothing is fetched. They are original, in the spirit of note blocks and the XP orb, not copies of Minecraft's: a link click is a pling that climbs a pentatonic scale with each click of the game (played when the navigation starts, so a slow load doesn't delay it), Back falls two notes, a dead link thuds (the frame posts `{mwr:'dead'}`), the checkpoint chimes from `celebrateCheckpoint`, and `finish` plays a fanfare for a win, a longer one for a new personal best, a sad trombone for Six clicks and two falling notes for giving up. The `AudioContext` is made on the first sound, which always follows a click or key press, as browsers require, and any audio error is swallowed. Sound is on by default, muted with the Sound checkbox beside Theme or the speaker button in the game header (`setSound`).

**Phones.** At 720 px and below the setup cards stack, Start game spans the width, and Recent games shows each game as lines (route, settings, clicks · time · date) instead of table columns. On a phone held upright (also taller than 500 px) the game header puts the objective on its own row above clicks, time and the buttons, and the path sidebar becomes one line of breadcrumbs that scrolls sideways, kept at its newest entry by `scrollPathToEnd` (also on resize, as turning the phone switches layouts), with a faded left edge while there is more to the left (`markPathScroll`), Hide beside it and the credit under it. Any screen 500 px tall or less, such as a phone on its side, keeps the sidebar at 160 px instead. On touch screens (`pointer: coarse`) inputs use 16 px text so iOS doesn't zoom on focus and the small controls are bigger. The game is `100dvh` tall so phone toolbars don't cover it. Inside the frame the article's padding narrows below 600 px, and the hover tint only applies with `(hover: hover)`, since on a touch screen it would stay on the tapped link. The wiki's own CSS already makes wide tables scroll sideways.

**Persistence.** `localStorage` key `mwr.history` holds the last 50 results and is used for the recent-games table and the per-pair personal best. Storage is shared with every page on the origin and open to the player, so it is read through `savedGames()`, which leaves out anything `isRecord` doesn't accept as a record `finish` would write (the wrong types, or a rule, topic or Content key that doesn't exist). A record lost to Six clicks has `outOfClicks: true`, and a Checkpoint game has `via` (the checkpoint's title), which is part of the personal-best key along with start, target and rules. Each record has `rules` (an array of rule keys), and the personal best only compares records with the same rules (`sameRules`). A rolled target's `topic` is recorded too, and so is `game.content` as `content` when anything was on (neither part of the personal-best key, since the cards already fix the game; `isRecord` only accepts `TOPICS` and `CONTENT` keys). The Settings column and the result note show the topic when it isn't Any and the Content as "Content: April Fools, Dungeons" (`settingsText`), and the Settings column marks a daily with its date. The Clear history link above the table empties it, dailies included, after a confirmation dialog. `mwr.theme` holds the chosen theme, `mwr.sound` whether sound is on, and `mwr.pathCollapsed` whether the path sidebar is collapsed (`setPathCollapsed`). Access goes through the `store` wrapper, which swallows storage errors.
