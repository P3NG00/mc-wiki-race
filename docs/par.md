# Par, golf and the result window

Part of the architecture, which is all in `index.html`.

## Par and Golf

Par is the fewest clicks for a pair, going by the snapshot. The setup screen works it out beside Start (`updateSetupPar`, run from every `renderCard`, so the first card rendered starts loading the graph and it is ready by the time a game starts), `startGame` works it out for the game (`game.parReady`, then `game.par`, for the header), but the setup screen and the header only show it with the Distance rule on (`#setupPar` and `#hudParStat` are hidden otherwise, and Exact clicks's `#exactInfo` gives only its count), since par says how far the target is, as Distance does. The result scores a win against it as golf does, each name with what it means for anyone who doesn't play golf (`golfScore` gives `{ name, note, over }`: Hole in one! (par 1 in one click), Par (even with par), Bogey (1 over par), Double bogey, Triple bogey, then just "N over par"; under par, possible only where par isn't the live fewest clicks (see below), Birdie (1 under par), Eagle, Albatross, then just "N under par"; `golfText` writes it in one line for the copied result) and shows one shortest route (`showPar` fills the score badge `#mScore`, orange when over par, the Par tile, the shortest route column `#mBest` and the wiki-date line `#par` once it knows, unless that result has been closed).

## The result window

The result window (`finish`, `.result`) goes: the outcome as the heading (a loss in the target colour, with its reason under it) and the golf score beside it; the game and its extra rules as labels, like the header's, with the route and the settings the labels don't say; four tiles (clicks, or "2 of 4" for Exact clicks, par, time, time per click); the personal best (a green bar when it is a new one); your path, each page marked with what it was (back, a checkpoint, a find, the target, stranded) and with how many clicks it was from what was next as it arrived (`togo`, filled in once every arrival is measured, `measured`; see Distance in [rules.md](rules.md)), in the target colour (`worse`) where a click got no closer to the same objective, but for Exact clicks, which has to take detours, with a line over it saying how many clicks got no closer (`#mPathSum`, or that every one got closer when every page could be measured; none for Exact clicks) and a note under it saying what the numbers are, both only once something could be measured; beside it, the shortest route (for Exact clicks, a route of its count); then Share, Copy challenge link, Retry this pair and New game. Both copy `game.link`, made at `startGame` from the setup that started the game by `gameLink`, which the setup screen's Copy challenge link uses too: the sealed challenge link, or for a daily `#daily=<date>`, since the blob never holds a daily and its game wouldn't count as one. Share (`shareText`) copies the game's labels and settings, the route, the result with par and its golf name, your path with each page's count in brackets (from the result's own path entries, `steps`, so a record from the history alone has none) and that link. Under Blind target it names only the start (`shareRouteText`, the rest as ?) and leaves the path out, so the text gives away nothing the link holds unseen. On a narrow screen the tiles go two across and New game takes the full width above the others. The record keeps `par`, added afterwards to a record saved before it was known, and the history and Share show it. `parRoute` loads the graph the game was played on (`linkGraph`: `wiki-links.js`, and `wiki-navboxes.js` for Relaxed, each the first time it is needed, refused if its sha256 isn't `WIKI_DATA`'s) and searches it breadth-first (`shortestRoute`), opening each navbox once, the first and nearest time it is reached. Of the routes with the fewest clicks it takes one through the fewest pages that aren't content (`CONTENT_PAGES`: no topic and no family), then the first by page number, by taking each level of the search in that order. Version pages, data values and lists link to most of the wiki, and by page number alone ("Bedrock Edition …" sorts early) 6 in 10 routes shown on this snapshot went through one; now 1 in 10 do, the rest having no route through content alone as short. Par is the same either way. It follows the game's settings: navbox links only count in Relaxed, hubs are dead in Hard but the target's and the checkpoints' (`routeUsable`), a spin-off's pages only count when it is on, and the checkpoints split the route into legs (`legsRoute`). A round trip is the way there plus the way back, each through its own checkpoints (`roundTripRoute`). The way back can't use a page of the way there but the stops still ahead, which makes the fewest clicks a shortest loop through given pages, NP-hard in general, so it tries the shortest way there with the shortest way back around it and the other way about, then again with each page of those banned in turn (up to `ROUND_TRIP_TRIES`), stopping at the lower bound, the shortest way there plus the shortest way back. On this snapshot it reached that bound in all of 898 pairs tried in Normal, Relaxed and Hard and all of 398 with a checkpoint each way, so par is exact in practice. Scavenger's par is exact too: for articles the shortest over every order (`huntRoute`, `orders`), since revisits are allowed, and for kinds a breadth-first search over (page, kinds found) (`kindsRoute`), which goes by the snapshot's members only, so a live-only find can beat it. With Round trip each goes home from its last find around the hunt: articles through `roundTripRoute` for each order, the orders taken by their lower bound, and kinds from each finished hunt in turn, nearest first, skipping those whose shortest way home at all (`distancesTo`) can't win, so these two are no longer exact. Live edits since the snapshot can make the real fewest clicks lower or higher, so the line names the snapshot's date. It also shows one route that takes that many.
