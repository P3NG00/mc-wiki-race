# Game rules and state

Part of the architecture, which is all in `index.html`. The state is the `game` object.

- `game.content` is the Content in play: what is on at `startGame`, plus the spin-off of any card's page (`spinoffOf`), whose links have to work to reach it, so a challenge link starting on `Dungeons:Creeper` needs no checkbox. `renderArticle` leaves its spin-offs out of the frame's dead namespaces. `toInfo` accepts a page in a spin-off's namespace by its number, taken from the ZIM's `ns-N` body classes, which match the live API's `ns`.
- *Difficulty* (`LEVELS`, the Difficulty row) is the rules No navboxes and No hubs: Relaxed has neither, Normal (the default) No navboxes, Hard both. The research behind it: with navboxes almost any sensible click gets closer ([RESEARCH.md](../tools/wikidata/RESEARCH.md)). The two rules stay rule keys, so `game.rules`, the frame, the personal-best key and challenge links treat them like any other rule, but the extra rules don't list them. `rules()` adds the difficulty's to the ticked ones, `setRules` sets the difficulty from them (`levelOf`), and `rulesText` names the difficulty unless it is Normal, so the Settings column shows "Hard" or "Relaxed".
- *Rules* are defined in `RULES`. The games' rules (Checkpoint, which the screen calls Relay, Scavenger, Exact clicks) can't be played together, so the game tiles pick one (`GAMES`, `gameMode()`; a Race has none), and the rest (`EXTRA_RULES`: Round trip, No Back, Blind target, Hot/cold, Six clicks) are checkboxes that go with any game but Exact clicks, which plays without Six clicks (it has its own count) and Round trip (it never visits a page twice): there those boxes are disabled and say why (`OFF_IN_EXACT`), and `rules()` leaves them out even if ticked. With Round trip on, each game's tile and strip say what it is then (`GAMES`' `trip`). All of these are `input.rule` checkboxes or the game radio, which `rules()` reads, and `setRules` sets the game from a set of rules with `gameOf` (a hand-made link with several games' rules plays the first of Exact clicks, Scavenger and Relay). `startGame` copies `rules()` into `game.rules` (sorted in `RULES` order), and everything during play and in `finish` reads that, never the checkboxes. Changing a rule or the difficulty doesn't reroll, but leaves a daily. *No Back* hides the Back button and is also enforced in `goBack()`. *No hubs* makes links to the hubs (`hubs` in `tools/wikidata/config.json`) dead: `HUB_TITLES` maps every hub and its redirects, those to sections included (about 1,000 titles, from `wiki-data.js`), to the hub, and `navigate` passes all of them except the target's hub to `renderArticle` as `blocked`. Going Back to a hub start is allowed, and a hub that is a checkpoint stays live too. *Blind target* keeps every card but the start, and Scavenger's kinds, off the setup screen (`hiddenKeys`): they stay empty until Start picks them (`pickHidden`, through `reroll(…, true)`, with a target par holding as usual and for Exact clicks a target with a route of its count, waiting on the latest `updateSetupPar` run, `setup.parRun`), or are held unseen when the game was fixed beforehand (the daily, a challenge link, and Copy challenge link, which picks them first since the link carries them, sealed). Their cards say Hidden and when each shows (`shownWhen`: when the game starts, or in a Relay when the stop before it in playing order is reached, the target among the checkpoints on a round trip), with no Reroll or custom box, Swap is hidden, and par and Exact clicks's count wait for the game. Any reroll, a new start, and any rule or difficulty change while it is on or just turned off (`setup.blind`, set by `setRules` and the change listener) drops them (`dropHidden`), so turning it off rolls new ones rather than showing the held ones; `renderCard` and `renderKinds` read the checkbox, and changing any rule re-renders the cards. A target par under it rerolls the start too, since only a start with a target at that par will do. During play it hides the picture and description in the HUD, behind the path and through the peek button, which is hidden, and in a Relay `renderObjective` shows a stop ahead as ? until the one before it is reached, all but the start a round trip goes back to. Scavenger's finds all show from the start, since they go in any order. *Hot/cold* hints after each arrival but the first and the objective's own (a target or later checkpoint passed early gets one) whether the page is closer to `objective()` than the page before it (`hotColdHint`: the fewest clicks from each, by the link graph under the game's settings, `routeUsable`, as par uses; a page with no route counts as farthest, so a dead end is colder): Warmer, Colder, Same distance, or No hint for a page the snapshot lacks. It never says how close. The hint goes onto the path entry (`hint`, a marker in the path list) and shows over the article (`showHint`, from the arrival once the hint is known and from `frameReady`, whichever comes last, and only for the latest arrival). It isn't a daily rule, since it makes a game easier. *Six clicks* shows the count as "of 6" under the clicks, with a dot a click (`#hudClicksK`, `#hudMeter`, from `game.limit`), and `navigate` ends the game as lost (`finish(false, 'outOfClicks')`) when an arrival that isn't the target uses up the last click. *Exact clicks* is a game too, and takes Six clicks's place: the target has to be reached in exactly par + `EXACT_EXTRA` (2) clicks, on no page twice. Revisits are out because a page almost always links back to the one before, which would make any count easy. So Back is hidden (`canGoBack`), every visited page is dead by every title that led to it (`game.dead`, renewed on each arrival), and reaching the target sooner loses (`tooSoon`), as does using up the count (`game.limit`, `outOfClicks`). The count can always be done: `updateSetupPar` finds a route of exactly that many clicks (`exactRoute`, `setup.exact`) and Start waits for it. That is NP-hard in general, so `exactRoute` searches depth first through pages the target can still be reached from in the clicks left (`distancesTo`, a breadth-first search back from the target over reverse edges made once per graph file), the farthest first, and gives up after `EXACT_BUDGET` pages. On this snapshot it found one of par + 2 for every one of 447 pairs tried, in a few milliseconds. The result shows that route, and a win gets no golf score, since every win is par + 2. *Scavenger* (the Scavenger hunt game): instead of a target there are `HUNT_SIZE` (3) things to find, in any order, chosen with `#huntMode` in its strip. *Articles* (`huntMode() === 'articles'`) puts them on the two checkpoint cards and the target card, labelled Find and joined by +. *Kinds* puts three kinds (`KINDS`, from `wiki-data.js`) on a card of their own (`#cardHunt`, `setup.kinds`, `setKinds`), each with its best-known members as examples; `rollKinds` takes them from three topics, none holding the start (`firstKinds`, which the daily uses too), and a new start in one of them rolls them again (`renderCard`), since the start never counts. `startGame` puts them in `game.hunt` (`{ info }` or `{ kind }`, with a label), with `game.goal` null, so the code that reads the objective asks `game.hunt` first (`huntLeft`, `ahead`, `cardTitles`). An arrival finds (`huntFinds`) an article by its title and a kind by its snapshot members or the page's live categories (`parse.categories`, asked for with every article) less the kind's exclusions, so a page added to a category since the snapshot counts. A page can find several kinds at once. Each find gets the checkpoint's banner ("✓ Found a Nether mob: Blaze (2 of 3)") and its path entry `found`; finding all wins. Hot/cold aims at the nearest of what is left. Swap reverses the articles, and is hidden for kinds.
- *No navboxes* removes the navbox tables, which link most game content to the rest of its family (on Diamond, 1,984 live links drop to 829). Popular and Deep cuts rank articles by their links from outside navboxes, and every target is linked from at least `MIN_BACKLINKS` articles outside them. *Checkpoint* adds one to three cards between start and target (the count is `#viaCount`, in the Relay's strip; `syncVia` shows the cards in use, numbers them when there is more than one, and rolls the empty ones). A relay of two or three is the same rule. `game.vias` must be reached in order (`game.viaNext` counts them, set in `navigate` from the post-redirect title, with that path entry's `via` set to the checkpoint's number) before arriving at the target counts; a later one reached early is an ordinary page. The header's route and the picture behind the path follow `objective()`: the next checkpoint until all are reached, then the target. Reaching one sets `game.celebrate`, and once that article has rendered `frameReady` calls `celebrateCheckpoint()`: a banner over the article naming what comes next (`#toast`, `showToast`, gone after 3 s or on the next navigation; its animation runs as long as it shows, and with no time it stays) and a flash of the HUD objective. Swap reverses the whole chain. *Round trip* goes with any game but Exact clicks: whatever the game asks, then back to the start, which the setup screen marks with "Start and finish" (and a ⇄ arrow when nothing stands between). In a Relay the checkpoints go around the target: `setup.back` (`backCount()`) of them come after it, on the way back, rolled with the cards (`rollBack`: one checkpoint either side, of two or three at least one each way) and kept, or moved to the nearest that fits, when the count changes. `placeTarget` moves the target card among the checkpoint cards, with its own arrow (`#goalArrow`), and Swap goes round the same loop from the target instead: the start and target change places and the checkpoints of the way back come first. `startGame` plays a round trip as a chain with the target as one more checkpoint (`game.turn`, its number among `game.vias`) and the start as `game.goal` (`game.roundTrip`), so the objective, the banner, Hot/cold and the win check need little of their own; `viaName` and `checkpointNumber` number the checkpoints around the target. Scavenger's heads for the start once nothing is left to find (`hunting()`, which `objective()` is null during). `finish` records it by its cards: the target as `goal`, the checkpoints as `vias` and `back`. Reaching the target, or the last find (`turnBack`), starts the Back stack again from there, so Back can't walk the way there backwards, and makes every page of the way there dead, the target included, but those still ahead (`ahead()`: the checkpoints of the way back and the start): `game.dead` holds their titles and the link titles that led to them, which `navigate` adds to `blocked` and Hot/cold avoids. If the snapshot has no way on around them, that arrival gets the `stranded` hint, saying only giving up is left. The path entry is marked in the accent colour. `CLICK_LIMIT` covers the whole route.
- While a game is on (`startGame` until `finish` or `toSetup`), a `beforeunload` listener (`guardLeaving`) makes closing the tab, reloading, the browser's Back and any other way of leaving the page ask first with the browser's own dialog. It is added and removed rather than left on, since a page with one may be kept out of the back/forward cache. Browsers only show the dialog after a real click or key press, and a game only starts from one (Start or Retry this pair). iOS Safari doesn't show it at all.
- `path` records every visit in order and drives the click count (`path.length - 1`).
- `stack` is the navigation stack for Back. Going back is recorded in `path` and counts as a click.
- The win check compares `parse.title`, which is the title after redirects, against the target's resolved title. Following a redirect to the target therefore counts as arriving.
- The clock pauses while an article is loading and rendering, and while the Give-up confirmation is open. It keeps running while the player peeks at the target description. `game.loading` stays set until the frame posts `{mwr:'ready', token}`. That message comes from its own `<script>` after the main frame script, so it is sent only after the render-blocking stylesheets have loaded. A 15 s timeout calls `frameReady` anyway. An article that fails to load (a network or HTTP error, a MediaWiki error, a reply that isn't JSON or has no article) shows Retry and Cancel with the clock stopped. Everything that can fail has to fail inside `navigate`'s `try`: an error after it would leave the game loading, with Give up disabled.
- `navToken` throws away responses from navigations that have been superseded, and stale `ready` messages too.
- `parseCache` keeps up to `PARSE_CACHE_MAX` parse results, stored under both the requested and the resolved title, and is cleared on return to setup. Back and "Retry this pair" don't refetch. The API marks parse responses uncacheable, so the browser's HTTP cache can't do this.
