# Themes, pictures, sounds, the game header and phones

Part of the architecture, which is all in `index.html`.

## Themes

A theme is the set of CSS variables on `:root` (colours, `--font`, `--radius*`) plus `color-scheme`, which also decides the article's wiki theme (`themeIsDark()` reads the computed `color-scheme`, falling back to `prefers-color-scheme` when it is ambiguous). Built in: Auto (no `data-theme` attribute, follows the OS), Light and Dark (`data-theme="light"`/`"dark"`). Auto's dark rule is `:root:not([data-theme])`, so no other theme ever picks up the dark variables. A page serving the game can add themes without editing this file: a `<link rel="stylesheet">` or `<style>` in `<head>` with `data-mwr-theme="Name"` that defines `:root[data-theme="Name"]`, plus `data-mwr-default` to make it the default. The names `auto`, `light` and `dark` belong to the built-ins (a host theme named `auto` could never apply). The `#theme-boot` script at the top of `<body>` runs before first paint: it builds `THEMES` (used by the main script) from those elements and applies the saved theme if it still exists, else the default, else Auto. It is not `<script>` followed by a newline on purpose, so the syntax-check regex still finds the main script. The picker on the setup screen calls `setTheme()`.

## Pictures

Thumbnails are requested at 400 px (`pithumbsize`). Every setup card and the path sidebar also show a large faded copy (`.art`, at `--art-opacity`, which themes can set) behind their content and cut off by the box's edges: the card's article, and in the sidebar `objective()`. The sidebar's is hidden on narrow screens. Pictures are drawn with hard edges (`image-rendering: pixelated`), except ones whose URL has `/thumb/`: the wiki serves small sprites at their own size (Diamond is 160 px), so a thumbnail URL means it scaled down a bigger render or screenshot, and those are drawn smoothly. A `/thumb/` `.art` also gets a radial mask, which softens a screenshot's rectangular edges.

## Sounds

Every sound is synthesized with Web Audio when it plays (`SOUNDS`, played through `play()`), so there are no sound files and nothing is fetched. They are original, in the spirit of note blocks and the XP orb, not copies of Minecraft's: a link click is a pling that climbs a pentatonic scale with each click of the game (played when the navigation starts, so a slow load doesn't delay it), Back falls two notes, a dead link thuds (the frame posts `{mwr:'dead'}`), the checkpoint chimes from `celebrateCheckpoint`, and `finish` plays a fanfare for a win, a longer one for a new personal best, a sad trombone for Six clicks and two falling notes for giving up. The `AudioContext` is made on the first sound, which always follows a click or key press, as browsers require, and any audio error is swallowed. Sound is on by default, muted with the Sound checkbox beside Theme or the speaker button in the game header (`setSound`).

## Timer

The Timer checkbox beside Sound (`#timerToggle`, remembered as `mwr.timer`) is for relaxed play. It is on by default, since the game is a race: clicks and time are its score, and the daily is meant for comparing results. `startGame` copies it into `game.timed`, so a game is timed or not throughout, and there is no switch in the game header. An untimed game hides the clock (`#hudTimeStat`, and no interval updating it), says nothing about time in the Give-up dialog or the peek, and its result has only the Clicks and Par tiles (`.tiles.untimed`). The clock still runs underneath, which keeps `navigate` and the pauses as they are, but `finish` records no `ms`, so the result, its personal-best note, Share and the daily box say clicks alone (`wonText`), and Recent games shows a dash for its time.

## The game header

The game header (`renderObjective`, redrawn when the objective changes) has the game and its extra rules as labels (`#hudTags`) with how far along it is ("1 of 2 checkpoints reached", "Found 1 of 3", "On the way back", Exact clicks's count), and with Distance on the latest arrival's count beside them (`#hudHint`, from `renderHud`). Under them is the route (`#hudRoute`): every stop as a chip, done (✓, a button), now (the objective, holding `#hudImg`, `#hudLbl` and `#hudGoal`) or ahead (dashed), joined by arrows; for Scavenger the things to find, found ones ticked with what found them. A route of more than `ROUTE_FULL` (3) stops shrinks the done chips to their ✓ (their names stay in a tooltip), and a click on one opens them all (`.route.open`); the row scrolls sideways when it still doesn't fit, kept on the objective by `scrollRouteToNow` (also on resize). The ? button beside it is the peek. On the right are the clicks (with a limit, "of 6" or "of exactly 4" and a dot a click), par (only with Distance on, `#hudParStat`; see [par.md](par.md)), time (unless the Timer is off), sound, Back and Give up.

## Phones

At 720 px and below the setup cards stack, Start game spans the width, and Recent games shows each game as a card (the labels and the day, the route, the result and time) instead of table columns. On a phone held upright (also taller than 500 px) the game header puts the labels and the route on their own rows above clicks, time and the buttons, Back shows only its arrow, and the path sidebar becomes one line of breadcrumbs that scrolls sideways, kept at its newest entry by `scrollPathToEnd` (also on resize, as turning the phone switches layouts), with a faded left edge while there is more to the left (`markPathScroll`), Hide beside it and the credit under it. Any screen 500 px tall or less, such as a phone on its side, keeps the sidebar at 160 px instead. On touch screens (`pointer: coarse`) inputs use 16 px text so iOS doesn't zoom on focus and the small controls are bigger. The game is `100dvh` tall so phone toolbars don't cover it. Inside the frame the article's padding narrows below 600 px, and the hover tint only applies with `(hover: hover)`, since on a touch screen it would stay on the tapped link. The wiki's own CSS already makes wide tables scroll sideways.
